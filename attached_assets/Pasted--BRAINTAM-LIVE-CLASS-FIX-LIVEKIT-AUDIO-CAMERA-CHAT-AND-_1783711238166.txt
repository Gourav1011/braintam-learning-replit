# REQUIRED BRAINTAM ROLE MODEL

Preserve this permission model exactly.

## Teacher/Admin

Teacher or authorized admin can:

* Publish camera
* Publish microphone
* Share screen
* Watch other approved stage participants
* Start polls
* Manage classroom
* Invite students on stage
* Remove students from stage
* Mute stage students
* Manage raise-hand requests

## Student

Student is viewer-only by default.

Student can:

* Watch teacher video
* Hear teacher audio
* Use permitted classroom chat
* Answer polls
* View leaderboard
* Raise hand
* Receive a stage invitation

Student cannot:

* Turn on camera freely
* Turn on microphone freely
* Share screen
* Publish media without teacher approval

Student camera and microphone may become available only after:

```text
Teacher invites student
→ Student receives invitation
→ Student accepts invitation
→ Backend grants temporary LiveKit publishing permission
→ LiveKit confirms permission
→ Student camera/microphone starts
→ Student appears on stage
```

The student must automatically return to viewer-only mode after the existing 60-second stage limit or when removed by the teacher.

## Mentor

Mentor is also viewer-only.

Mentor can:

* Watch teacher video
* Hear teacher audio
* View assigned mentor group
* Use permitted mentor/group chat
* View assigned students
* Suggest students to the teacher if supported
* Monitor attendance

Mentor cannot:

* Publish camera
* Publish microphone
* Share screen
* Receive student-stage publishing permission

Do not weaken backend permissions.

# MULTIPLE SIMULTANEOUS LIVE CLASSES

Braintam may run many live classes at the same time.

Examples:

```text
Live Class ID: 125
Course: Grade 6 Mastery
Subject: Mathematics
Teacher: Teacher A
LiveKit room:
braintam-live-125

Live Class ID: 126
Course: Grade 6 Mastery
Subject: Science
Teacher: Teacher B
LiveKit room:
braintam-live-126

Live Class ID: 127
Course: Grade 8 Ignite
Subject: English
Teacher: Teacher C
LiveKit room:
braintam-live-127
```

Every scheduled live-class database record must have its own isolated room.

Use the individual live-class database record ID as the stable room identifier.

Preferred fallback:

```ts
function roomNameFor(
  liveClassId: number
): string {
  return `braintam-live-${liveClassId}`;
}
```

Do not create rooms using only:

* Course ID
* Grade
* Subject
* Teacher ID
* Batch
* Date
* One global Braintam room

Different live-class records must always have different rooms.

All users joining the same live-class record must receive the same final room name.

Preserve `liveClassesTable.liveKitRoomName` as the database source of truth.

Required logic:

```ts
let roomName =
  liveClass.liveKitRoomName;

if (!roomName) {
  const generatedRoomName =
    `braintam-live-${liveClass.id}`;

  const [updated] = await db
    .update(liveClassesTable)
    .set({
      liveKitRoomName:
        generatedRoomName,
    })
    .where(
      and(
        eq(
          liveClassesTable.id,
          liveClass.id
        ),
        isNull(
          liveClassesTable.liveKitRoomName
        )
      )
    )
    .returning({
      liveKitRoomName:
        liveClassesTable.liveKitRoomName,
    });

  if (
    updated?.liveKitRoomName
  ) {
    roomName =
      updated.liveKitRoomName;
  } else {
    const [freshClass] =
      await db
        .select({
          liveKitRoomName:
            liveClassesTable
              .liveKitRoomName,
        })
        .from(
          liveClassesTable
        )
        .where(
          eq(
            liveClassesTable.id,
            liveClass.id
          )
        )
        .limit(1);

    roomName =
      freshClass
        ?.liveKitRoomName ??
      generatedRoomName;
  }
}
```

Adapt this to the repository’s actual Drizzle schema and imports.

Do not overwrite an existing non-null room name during a normal join.

Do not create a new random LiveKit room for each participant.

Socket.IO and LiveKit may use different room-name formats, but both must isolate participants by the same live-class record.

Example:

```text
Live Class ID:
125

Socket.IO room:
125

LiveKit room:
braintam-live-125
```

This is valid.

# FIX 1 — DECOUPLE LIVEKIT FROM SOCKET.IO

Inspect:

```text
artifacts/braintam/src/pages/live-classroom.tsx
```

The current implementation appears to initialize LiveKit using the Socket.IO connection status:

```ts
const livekit =
  useLiveKit({
    sessionId,
    enabled: connected,
  });
```

This creates an unnecessary dependency:

```text
Socket.IO fails
→ connected remains false
→ LiveKit never starts
→ No camera
→ No microphone
→ No teacher audio
→ No teacher video
```

Remove this dependency.

Socket.IO and LiveKit must connect independently.

Use separate connection states:

```ts
const {
  socket,
  connected:
    socketConnected,
} = useClassroomSocket(
  sessionId,
  userId,
  name,
  role,
  groupId,
  phone
);
```

LiveKit should start when:

* Authentication is resolved
* A real authenticated user exists
* The live-class session ID is valid
* The session is not a demo/fallback session

Example:

```ts
const hasValidSession =
  Boolean(sessionId) &&
  sessionId !== "demo" &&
  Number.isFinite(
    Number(sessionId)
  );

const livekit =
  useLiveKit({
    sessionId,
    enabled:
      hasValidSession &&
      Boolean(authIdentity),
  });
```

Adapt this to the actual authentication provider.

Do not repeatedly reconnect LiveKit because of unstable object references or unrelated React state changes.

Required behavior:

```text
Socket.IO disconnected
→ LiveKit video/audio continues

LiveKit reconnecting
→ Socket.IO chat/polls continue
```
